# C70 — the `hooks/list` oracle on codex-cli 0.154.0

> **Verdict: on 0.154.0 `codex app-server` still answers `hooks/list` in the shape C70 validates,
> for an empty population and for a real one; an all-`trusted` population is still unobserved on
> this version.** `common/codex_hooks.py` names 0.154.0 as the version its wire protocol was
> measured on, while every earlier `hooks/list` row in [MEASUREMENTS](../MEASUREMENTS.md) (M20–M24)
> names 0.149.1; this re-measures the oracle on the version now installed. Rows M49–M50. Owned by
> [C70](../TASKS.md).

## Method

- codex-cli 0.154.0 (`codex --version`), 2026-09-13.
- The query is akmon's own route: `common/runtime.py::codex_hooks_list_command()` (`codex
  app-server`) through `common/codex_hooks.py::query_hooks_list`. That function accepts only a
  clean answer — the request id echoed, exactly one `result.data` entry for the cwd, `hooks`,
  `warnings` and `errors` as lists, `errors` empty, every hook in the `HookMetadata` shape — and
  raises `CodexProtocolError` on anything else, so "answered" below means that whole shape held.
- The expected population is `expected_codex_hooks` over the root's `.codex/hooks.json`;
  `hook_trust_problems` joins it to the answer.
- Read-only on both roots: no trust granted, no config or consumer file written; `git diff
  --summary` in the akmon tree was empty afterwards.

## Results

| root | expected | reported | `trustStatus` | outcome |
|---|---|---|---|---|
| akmon source tree (no `.codex/hooks.json`) | 0 | 0 | — | clean answer, zero population |
| alphavar, a synced consumer (project trusted) | 4 | 4 | `modified` × 4 | clean answer; all four inert until re-approved in `/hooks` |

alphavar's `.codex/hooks.json` carries a staged, uncommitted change against its last commit:
all four commands move from `python3 "…/_aitna/.akmon/hooks/codex-hook.py" <mode>` to the
package-mode `"…/.venv/bin/akmon" hook codex-hook <mode>`, and one `PreToolUse` group's matcher
moves from `Edit|Write|apply_patch` to `Bash|apply_patch`. Every entry therefore differs from the
hash it was trusted at — M19–M21's per-entry trust, seen again on this version.

## What this does not show

- **A green population on 0.154.0.** Neither root had one: the source tree wires nothing and
  every alphavar entry is `modified`. A `trusted` answer on this version is still unobserved.
- **Delivery.** `hooks/list` reports trust, not execution (M20); no hook was run.
- **The protocol details the module names beyond the shape** — no Content-Length framing,
  `initialize` answered at once, the interleaved `remoteControl/status/changed` notification.
  The clean answers are consistent with them; none was observed on its own.
